Point about bahrti cCAF:
24. cCAF will not handle Gx Traffic. It would be catered through CCPC and OCC 
(MBC)
4. Support of ULI (User Location Information) is not considered in the Scope as 
cCAF does not support Gx traffic.

Apart from supporting 5G traffic, cCAF is going to cater 4G traffic (Gy, Ro, and Esy) as 
well

FWA setup is meant to support only offline charging that means EC nodes wouldn’t be 
integrated with cCAF. But in this intermediate setup TN/CH PLMNs prepaid, postpaid 
along with Account Finders are getting integrated to support the Bharti’s requirement


cCAF solution in Bharti network is going to be deployed in geo-red active/active setup 
to support prepaid, postpaid, and FWA traffic. Following services of cCAF is going to be 
implemented in Bharti network:
1. 5G Converged charging – online & offline charging over N40 interface.
2. 5G Spending limit control (or policy control) over E-N28 interface.
3. 4G Data charging over Gy.
4. 4G VoLTE charging over Ro.
5. 4G policy control over Esy.

For offline charging i.e., in FWA setup it’s expected that SMF sends charging requests 
without RSU in all the create/update/release while quotaManagementIndicator should 
be OFFLINE_CHARGING in update and release messages.

00728791 — Punith S to Ericsson AB* Only 
After discussing with DU we came to know that Failover/Fallback of EDM is best possible WA to avoid duplicate CDR generation.
 
Here's the procedure.
 
EDM Failover:
 
1. Login to BAM CLI
 
2. Check which site is the Primary Site since commands to perform failover and failback needs to be run from Primary Site:
 
$ bamctl bam-cm-agent get-config
(Parameter “isPrimary” is true.)
 
3. Login to BEAM CLI on Primary Site
 
4. Check current configuration for EDM Global Partition id 0:
$ beamctl orchestrator get-partition-for-datatype 0 global edm -o yaml
 
5. Check current configuration for EDM for all Customer Partitions:
$ beamctl orchestrator get-partition-for-datatype <customer partition ID> customer edm -o yaml
Example:
$ beamctl orchestrator get-partition-for-datatype 1 customer edm -o yaml
$ beamctl orchestrator get-partition-for-datatype 2 customer edm -o yaml
 
6. Check the configmap containing currentstate for edm1 and for edm2:
$ kubectl -n <namespace> describe configmap eric-bss-edm-publishing-<edm application group>-currentstate-configmap
 
Example:
$ k describe configmap eric-bss-edm-publishing-edm1-currentstate-configmap
 
7. Check the configmap containing wantedstate for both edm1 and edm2:
 
$ k describe configmap eric-bss-edm-wantedstate-configmap
 
8. Trigger EDM Application Group failover for edm1:
$ beamctl orchestrator failover-appgroup edm1
 
9. Check status of the failover:
$beamctl orchestrator get-status
 
When parameter “operation” is set to failover, the failover is ongoing.
 "operation": "failover"
When parameter “operation” is empty, the failover is done.
 "operation": ""
 
10. Check the current updated configuration for all partitions again after failover.
 
11. Check the configmaps containing currentstate and wanted state again after failover
 
EDM restart:
 
1. From the counters, verify EDM publishing count comes down to zero.
 
2. Perform Rolling restart of EDM.
 
3. Verify all EDM collector threads are registered in zookeeper.
 
Fallback:
 
1. Trigger EDM Application Group failback for edm1:
$beamctl orchestrator failback-appgroup edm1
 
2. Check status of the failback:
$beamctl orchestrator get-status
When parameter “operation” is set to failback, the failback is ongoing.
 "operation": "failback"
 
When parameter “operation” is empty, the failback is done.
 "operation": ""
 
3. Check the current updated configuration for all partitions again after failback. The output from the commands should now look the same as before failover was triggered.
 
4. Check the configmaps containing currentstate and wantedstate again after failback. The output from the commands should now look the same as before failover was triggered.
 
CU will plan this activity and they confirmed for the closure of CSR.
